# RubiGUI 外部配布 設計書

- 作成日: 2026-09-10
- 対象: RubiGUI Word版 / PowerPoint版
- 状態: 設計確定（実装前）

---

## 1. 背景と目的

RubiGUI はこれまで職場内でのみ配布してきた。対面でサポートでき、配布相手も限られていたため、
zip を Google Drive に置いて直接渡す運用で足りていた。権利関係も検討の必要がなかった。

職場外から利用希望があり、管理職の了解を得て外部配布することになった。
**了解の条件は「作者の負担にならないこと」**であり、これを設計上の制約条件として扱う。

本設計書は、外部配布にあたって必要な準備の全体像を定める。

## 2. 前提と決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 配布範囲 | 同業のクローズドな範囲（数十人規模） | 一般公開はしない |
| 窓口 | 相手方に取りまとめ役を1名立ててもらう | 一次質問を相手側で吸収し、作者に届くのを真の不具合に限る |
| 著作権の帰属 | 作者本人（私的に開発したもの） | 職務著作に該当しない |
| ライセンス | MIT / `Copyright (c) 2026 Milli-Q13` | 条文が短く免責が明確。独自条件は解釈の問い合わせを生むため採らない |
| 通信機能 | **実装しない** | 「一切通信しない」と言い切れることが導入時の説明で強い。プロキシ起因の新規サポート案件を作らない |
| 配布形態 | Word版・PPT版を1つのzipにまとめ、辞書を共有（案B） | ダウンロード約396MB（別配布なら計756MB）。`override.json` が共有され読みの登録が1回で済む |
| 辞書 | SudachiDict-full 20250515 を同梱。当面更新しない | 更新は出力の変更であり、急ぐ理由がない |
| コード署名 | 当面見送り | 費用対効果。手順書で SmartScreen に対応する |
| 配布版数 | Word **v3.1** / PPT **v1.3** | 設定保存の挙動が変わる修正を含むため、パッチではなくマイナーを上げる |

## 3. スコープ

### 含むもの
- 配布物の構成の確定と、混入防止の仕組み
- ライセンス表記（MIT）と第三者ライセンス告知
- 導入手順書（PDF）の作成、既存 readme.txt の外部向け改訂
- サポート窓口（Googleフォーム）とサポート方針の明記
- リリース作業のスクリプト化
- 配布経路の整備（GitHub Releases 正本 + Google Drive ミラー）
- 上記に必要なコード修正 3点（§9）

### 含まないもの

- 同梱辞書の更新
- 一般公開・有償化

## 4. 配布物の構成

1つの zip に両版をまとめ、**同一フォルダに両方の exe を置いて辞書と辞書設定を共有する**。

Word版とPPT版で版番号が異なるため、**同梱物全体の識別子は配布年月**とする。

```
RubiGUI_2026-09/
  RubiGUI_Word_v3.1.exe
  RubiGUI_PPT_v1.3.exe
  RubiGUI_V31.bas                  ← Word版のみ使用
  system_full.dic                  ← 両版で共有（359.8MB）
  sudachi.json                     ← 両版で共有
  override.json                    ← 両版で共有（配布用の既定値）
  ruby_settings.json               ← 両版で共有（§9-1 の修正が前提）
  はじめにお読みください.pdf
  readme_Word.txt
  readme_PPT.txt
  LICENSE.txt
  THIRD-PARTY-NOTICES.txt
```

**配布物に入れないもの**: `*.py` / `*.log` / `__pycache__/` / `requirements.txt` / `tests/` / `test/`

### 混入防止

現在の「フォルダごと zip に固める」方式は危険である。実際に `RubiGUI_word_v3.0/rubigui.log` には
実在の授業プリント名とローカルパス（ユーザー名を含む）が記録されていた。`.gitignore` は
`*.log` を除外しているが、zip の作成は git を経由しないため効かない。

対策として、**配布物に入れるファイルを明示的に列挙する方式**に変える（§8）。
除外リスト方式ではなく許可リスト方式にすることで、新しい種類のファイルが増えても既定で入らない。

### override.json の配布用既定値

現在の内容（`ひつまぶし` / `名古屋` / `今日`）は動作確認用のデータである。
書式の見本になる語を数語だけ入れた状態に差し替える。空にはしない（書き方が分からず問い合わせになるため）。

## 5. ライセンスと権利表記

### LICENSE.txt
MIT ライセンスの英文正文を置き、その下に「参考訳（正文は上記英文）」として日本語訳を併記する。
MIT に公式の日本語訳は存在しないため、正文が英語であることを明示する。

### THIRD-PARTY-NOTICES.txt
同梱物のライセンス告知をまとめた1ファイル。**生成スクリプトで作る**（手書きすると更新を忘れる）。

ただし**すべてを自動収集できるわけではない**。確認したところ SudachiPy は配布物に
ライセンスファイルを同梱していない（`importlib.metadata.files()` に LICENSE が現れない）。
自動収集できないものは `packaging/licenses/` にライセンス本文を手置きし、
スクリプトが「収集分＋手置き分」を結合する形にする。
**収集も手置きも無い同梱物があればスクリプトを停止させる**（告知漏れのまま配布しないため）。

| 同梱物 | ライセンス | 備考 |
|---|---|---|
| SudachiPy | Apache-2.0 | |
| SudachiDict-full | Apache-2.0 | **`LEGAL` の全文添付が必須**。UniDic（BSD-3、著作権表示の再生産義務）、NEologd（はてなキーワード・日本郵便データ由来）の告知を含む |
| tkinterdnd2 / tkdnd | MIT | |
| jaconv | MIT | |
| pywin32 | PSF | |
| PyInstaller | GPLv2+ **例外条項付き** | 固めた成果物は任意のライセンスで配布可 |
| Python / Tcl/Tk | PSF / BSD | |

コピーレフトのものは無く、RubiGUI 本体のソース公開義務は生じない。

## 6. サポート体制

負担の原因と対策の対応は次のとおり。

| 負担の原因 | 対策 |
|---|---|
| Wordマクロの手動インポートでつまずく | 手順書にスクリーンショットを付ける（§7） |
| SmartScreen 警告に全員が遭遇する | 手順書の冒頭に置く |
| 「動きません」だけの問い合わせが来る | Googleフォームで版番号・OS・Officeの版・ログ添付・再現手順を必須項目にする |
| 「直してもらえる」と期待される | サポート方針を readme に明記する |
| 配布のたびの手作業 | リリース作業をスクリプト化する（§8） |
| 個別対応が発生する | 取りまとめ役を経由する運用にする |

### サポート方針（readme に明記する内容）
- 無保証であること
- 対応は可能な範囲で行うものであり、約束ではないこと
- 緊急対応はできないこと
- **職場は配布主体ではなく、問い合わせ先でもないこと**

### 窓口
Googleフォーム1つ。GitHub Issues は使わない（配布相手が GitHub アカウントを持たないため）。
届いた報告は作者が必要に応じて Issue に起こす。問い合わせは原則として取りまとめ役を経由する。

## 7. 導入手順書（はじめにお読みください.pdf）

既存 readme.txt（Word版527行）は詳細マニュアルとして残し、
**最初の30分に必要なことだけ**を別紙 PDF にする。Word で作成して PDF 出力する。

つまずく順に並べる。

1. **zip は必ず展開してから使う** — zip 内から直接 exe を実行すると辞書が見つからず起動に失敗する
2. **置き場所は OneDrive の同期フォルダを避ける**（例 `C:\RubiGUI`）— 同期タイミングで作業ファイルが復活する既知の問題がある
3. **ダウンロードと展開に時間がかかる予告** — 辞書が360MBある
4. **SmartScreen 警告の通り方**（スクリーンショット）
5. **PowerPoint版を使う** — マクロ不要。すぐ使える
6. **Word版を使う** — マクロ `RubiGUI_V31.bas` の導入が必要（スクリーンショット）
7. **困ったときは** — 取りまとめ役へ

Wordマクロの導入は Word版だけの作業であるため、章を分ける。
PPT版はマクロ導入が無く導入のつまずきが構造的に少ないので、PPT版から試してもらう案内にする。

### 既存 readme.txt の改訂
職場前提・開発者向けの記述を落とす。「exe にする場合（PyInstaller）」の節が該当する。
全体を通して同種の記述がないか洗い出す。Word版・PPT版でファイルを分ける。

## 8. リリース作業のスクリプト化

`packaging/make_dist.py` を新規に作る。

処理内容:
1. 許可リストに挙げたファイルだけを集めて配布フォルダを組む
2. `THIRD-PARTY-NOTICES.txt` をインストール済みパッケージのライセンスファイルから生成する
3. `LICENSE.txt` を配置する
4. zip 化する
5. **SHA-256 を算出して表示・記録する**
6. **最終チェック**: `.log` / `__pycache__` / `.py` / `requirements.txt` が混入していないか検査し、
   1つでもあれば停止する

既存の `packaging/build_exe.py`（exe のビルド）とは役割を分ける。

## 9. 必要なコード修正

### 9-1. `save_settings()` のマージ書き込み化（Word・PPT両方）【必須】

両版とも設定ファイルは `APP_DIR / "ruby_settings.json"` で名前が同じであり、
`save_settings()` は `json.dump(settings)` で**自分が持つキーだけを書き出す**。

| キー | Word版 | PPT版 |
|---|---|---|
| `ruby_mode` / `ruby_ratio` / `ruby_offset` | ○ | ○ |
| `line_spacing` / `include_title` | — | ○ |

同一フォルダに置くと、PPT版で行間や「タイトル枠も対象にする」を設定したあと
Word版が設定を保存した時点で、`line_spacing` と `include_title` が失われる。
読み込み側は未知のキーを無視するため気づきにくく、「設定したはずなのに戻っている」という
報告になる。**案B（同梱）を採る以上、必ず直す必要がある。**

修正方針: 保存時に既存ファイルを読み込み、自分のキーだけを更新して書き戻す。

### 9-2. 起動時にログへ版番号を記録（Word・PPT両方）

現在、ログに版番号が残っていない。起動時に1行記録することで、
ログを添付してもらうだけで版が確定する。報告者が版を書き間違えても困らない。

### 9-3. exe 名の変更

```
RubiGUI_V3.0.exe      →  RubiGUI_Word_v3.1.exe
RubiGUI_PPT_V1.2.exe  →  RubiGUI_PPT_v1.3.exe
```

同一フォルダに2つ並ぶため、現在の名前ではどちらが Word 用か分からない。
設定の読み先は exe 名ではなくフォルダ基準なので、改名による動作への影響はない。
`packaging/build_exe.py` の `--name` を変更する。

あわせてマクロのファイル名・モジュール名・マクロ名を版に追随させる
（`RubiGUI_V31.bas` / モジュール名 `RubiGUI_V31` / マクロ名 `InsertFuriganaFromTSV_V31`）。
これは版ごとに改名する既存の方針に従うものである。触る箇所は次の3つ。

- `.bas` ファイル自体（ファイル名・`Attribute VB_Name`・マクロ名）
- Word版 Python の `MACRO_NAME` 定数
- readme と手順書のマクロ導入手順（旧 `RubiGUI_V30` の削除案内を含む）

## 10. 配布経路

**正本は GitHub Releases。** 版ごとに URL が固定され、リリースノートに SHA-256 を記載できる。
1ファイル 2GB まで置けるため、辞書込み約396MB の zip をそのまま置ける
（リポジトリ本体の 100MB 制限は Releases には適用されない）。
`.gitignore` の「exe と dic は git 管理しない」方針は変更しない。

**相手先で GitHub が閲覧できるとは限らない。** 配布開始前に、取りまとめ役の方に
「御校で GitHub は開けるか」を確認してもらう。開けない場合に備えて、
**同一の zip を Google Drive にもミラーする**。SHA-256 が一致するため、
どちらから取得しても同一物であることを確認できる。

**更新の告知は取りまとめ役へメール1通。** アプリに通信機能は入れない。

## 11. 検証方法

1. `make_dist.py` が生成した zip を展開し、`.log` / `__pycache__` / `.py` /
   `requirements.txt` が含まれないことを確認する
2. 配布物を OneDrive 同期外のクリーンなフォルダに展開し、両方の exe が起動することを確認する
3. **設定衝突の回帰テスト**: PPT版で `line_spacing` と `include_title` を変更 →
   Word版を起動して設定を保存 → PPT版を再起動し、変更が保持されていることを確認する
4. 既存のフィクスチャ（`tests/`）で Word版・PPT版の出力が改修前と一致することを確認する
5. 公開した zip をダウンロードし直し、SHA-256 が記録値と一致することを確認する

## 12. 残課題

- コード署名証明書（SmartScreen の恒久対策）は見送り。要望が増えた段階で再検討する
- 同梱辞書の更新（現在 5世代・約16か月遅れ）。出力が変わる変更であるため、
  更新する場合は「新機能」ではなく「挙動の変更」として扱う
